# 機會評估分數卡與業務線

追蹤 Issue #24。本文件只描述程式與資料結構；評分名單不放在這個公開儲存庫。

## 用途

- **機會評估**：專案狀態是「提案中」時，專案多一個「機會評估」分頁。五個面向（財務貢獻、長期商業價值、社會影響力、人力可負擔性、成果確定性）各打 1–5 分，5 分最有利，可以附一句理由。
- 畫面顯示評分人數、平均總分（滿分 25）、各面向平均，並標出兩種情況：「偏低」（平均 ≤ 1.5）、「意見分歧」（最高與最低差 2 分以上）。**不會自動決定。**
- 管理者記錄「接／不接／先驗證」與理由；選「不接」時可以一鍵把狀態改成「未成案」。
- **業務線**：與年度預算的通路一致，才能直接對照目標：2C 零售、2B 禮盒、2B 專案、2G 政府／補助。這是分析與訂目標用的標籤，不是組織部門。

| 專案分類 | 預設業務線 |
| --- | --- |
| 2C零售（含市集） | 2C 零售 |
| 禮盒 | 2B 禮盒 |
| 企業、好田、中介、委外 | 2B 專案 |
| 政府 | 2G 政府／補助 |
| 其他 | 待分類 |

管理者可以在專案「基本資料」逐案調整業務線。

## 權限（全部在後端判斷）

| 動作 | 誰可以 |
| --- | --- |
| 看到機會評估 | 管理者，以及指令碼屬性 `OPP_SCORERS` 名單內的人 |
| 新增、修改、撤回分數 | 同上，而且只能動**自己的**那一筆（姓名取自伺服器端通行證） |
| 記錄或清除決定 | 管理者 |
| 調整業務線 | 管理者 |

- `OPP_SCORERS` 沒設定或格式錯誤時，只有管理者能看、能評分（fail closed）。
- 不在名單的人：讀取時 `_opp` 整個拿掉；就算直接送出 `_opp` 也一律忽略。
- 分數和業務線都不是財務數字，不受專案財務權限影響。

## 資料結構

存在 `State` 的 `_opp`（與專案列分開）：

```
_opp: {
  <專案 id>: {
    scores:   { <姓名>: { fin, value, impact, capacity, certainty, note, at } },   // 1–5 整數；note ≤ 300 字
    decision: { result: 接|不接|先驗證, reason, by, at } | null                     // reason ≤ 500 字
  }
}
```

專案列多一個管理者欄位 `bizLine`（`null` 表示依分類自動推得）。

## 正式 GAS 的接點

新增檔案 `gas/OppScore.gs`（照貼）。主程式（程式碼.gs）改五處：

1. `ADMIN_FIELDS` 加上 `'bizLine'`：
   ```js
   const ADMIN_FIELDS = ['assignee', 'catOverride', 'deleted', 'deletedAt', 'deletedBy', 'bizLine'];
   ```
2. `cleanField_` 的 `switch` 加一行：
   ```js
   case 'bizLine': return cleanBizLine_(v);
   ```
3. `rowDefaults` 最後一個欄位後加上 `, bizLine:r.bizLine||null`（網頁與 GAS 共用的那一份，兩邊一致）。
4. `redact_` 在 `return out;` 前加一行：
   ```js
   oppRedact_(out, state, user);
   ```
   （迴圈會先把 `_opp` 原樣複製，這一行再依名單保留或拿掉。）
5. `mergeWrite_` 在 `known` 算完之後（專案列迴圈前）加：
   ```js
   if (incoming._opp !== undefined) {
     out._opp = oppMerge_(stored._opp, incoming._opp, me, known, oppScorers_(), Date.now());
     if (!Object.keys(out._opp).length) delete out._opp;
   }
   ```

指令碼屬性：`OPP_SCORERS = ["<權限分頁 A 欄的確切名稱>", …]`。管理者不用列入。

部署順序：先更新 GAS（新版本），再合併前端。舊版 GAS 會丟掉 `_opp`，前端也就不會出現「機會評估」分頁，其他功能不受影響。

## 經營檢視的調整（對焦年度預算）

| 區塊 | 內容 |
| --- | --- |
| A. 年度經營目標 | 原有：年度營收預算、淨利目標、年初至今淨利與達成率 |
| B. 季度目標對照 | 營收、毛利、毛利率、營業費用、營業外收入、稅前損益：Q1–Q4、累計、全年的目標與實際 |
| C. 剩餘月份營收門檻 | 用已結束月份的實際數回推，要達到全年稅後淨利目標，剩下的月份至少要做多少營收；毛利率、費用、補助三個假設可以在畫面上調整（不存檔），並對照儀表板上同期間的專案預估 |
| D. 業務線 × 目標 | 各業務線全年目標、累計實際與達成率、剩餘月份目標、儀表板預估、毛利率目標（有匯入通路成本時才顯示） |
| E. 經營風險與待決策事項 | 原 B 區；「需要主管決策」改成「提案中、尚未決定的新機會」 |
| F. 新機會評估 | 提案中或已有評分的機會：平均總分、需要討論的面向、決定 |

已移除「業務經營分類」「部門 × 業務」「週會決策紀錄」三區。

### 財務摘要的新格式（向下相容）

- 指標代碼新增：`cogs` 銷貨成本、`gross_profit` 毛利、`opex` 營業費用、`op_income` 營業淨利、`nonop_income` 營業外收入、`pretax` 稅前損益。
- 每月一列（期間 `month`，截至月份＝該月），預算與實際可以放同一列，也可以分開放；同一指標、同一業務線、同一月份各取更新日期最新的預算與實際。
- 選填第 14 欄「業務線」：空白＝全公司，其餘只接受 `2C 零售`、`2B 禮盒`、`2B 專案`、`2G 政府／補助`。原本 13 欄的表頭仍可讀。
- 稅率依年度 `pretax` 預算與 `net_income` 目標換算；沒有 `pretax` 預算時假設 20%，畫面會標示「假設」。
- 後端 `execRead` 仍會讀「週會決策紀錄」分頁（不影響），之後的部門會議功能再決定要不要沿用。
