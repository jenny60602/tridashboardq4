# 發布與回復手冊

本文件定義發布與回復要求，不是部署成功紀錄；缺少下列版本證據時，不開始正式更新。

AI 先依 [AI 工作流程](AI_WORKFLOW.md)分開核對技術準備度、業務驗收與操作授權。一般同事的「符合需求」不能補足技術缺口；已存在且範圍相符的發布授權則直接沿用，不重問。這份發布紀錄引用同一份變更紀錄，不另造一組通過狀態。

**合併是獨立的人為決定。** 所有修改先有工作分支與 Issue，再以 PR 交付。人看過交付結果後，自行合併或明確指示 AI 合併特定 PR 的已交付版本；AI 記錄對應 head，不要求一般同事提供提交編號。沒有這項決定，PR 保持開啟，AI 不得合併、啟用 auto-merge 或加入 merge queue。發布授權、檢查通過與其他 PR 的授權不能取代本 PR 的合併決定。

## 先判斷本次範圍

僅修改說明文件、空白範本或 Git 忽略規則，且未變更應用程式、部署設定及可執行工作流程時，可以將 GAS 配對、正式資料備份及互動驗收標為不適用並寫明理由。這類變更檢查文件內容、連結、JSON、公開範圍與差異，不要求重跑不相關的應用程式測試，也不需要取得 GAS 部署權限。

若合併會觸發靜態網站發布，仍記錄該工作的結果與前端應用程式檔案比對；「程式內容未變」不等於「沒有發布工作」。其餘發布項目依實際變更範圍套用。

## 每次發布要留下的一份紀錄

紀錄存放在公司受限位置，不附正式資料內容、密碼或 token。使用以下空白範本：

```text
變更用途／使用者影響：
工作分支／Issue：
PR 與精確前端提交：
人的合併決定／對應 PR head／可信授權來源（未決定就明列）：
目前 GAS 部署版本／程式雜湊：
預計 GAS 部署版本／程式雜湊：
前後端相容約定（驗證方式、動作、欄位、角色）：
資料格式有無改變；舊版本能否理解新欄位：
保留同一部署或變更端點的理由：
假資料驗證結果及對應版本：
私有備份位置／建立時間／必要範圍：
回復的前端＋GAS 配對；資料能否沿用：
失敗時停止條件／回復負責人：
發布人／檢查人／業務窗口：
預計窗口／是否影響已開啟的分頁：
實際版本與發布結果：
驗收證據／未驗證項目：
```

不把私有資源 ID 或備份連結放進公開 PR。若需要依部署 ID 核對，放在上述受限紀錄。

## 發布前

1. 重新核對遠端 main、PR head 與已儲存 GAS 原始碼。來源有變就重新整合，不以昨天的測試結果替今天不同的程式背書。
2. 確認發布者能更新既有 GAS 部署與前端發布來源；權限不足時停在修改前，不建立另一個不明用途的正式部署。
3. 核對前後端的驗證方式、動作與回傳欄位。相同 API 版本號只能是一部分條件，不能作為完整相容證明。
4. 將新舊前端及新舊 GAS 的組合，在獨立假資料環境確認。至少涵蓋登入拒絕、角色範圍、讀寫、登出／到期、晚到回應、同步失敗與此次改動欄位。
5. 保留目前程式與部署版本。依變更影響備份必要資料，核對時間、存取權與保存位置；副本建立成功不等於已完成復原演練。正式備份不拿來測試。
6. 填入回復條件。如果新增資料欄位可能被舊程式忽略、覆蓋或誤算，先安排可行的回復策略，不能只說「退回上一版」。

## 決定更新順序

不要對所有版本一律套用「後端先、前端後」。只有新後端仍可服務當時的舊前端時，才能先更新 GAS 再發布前端。

若登入協定互不相容，應先做受控的過渡相容版本，或安排明確的維護窗口並一起切換。過渡支援必須有授權與移除期限，不能為了相容而重新允許匿名讀寫。也要處理仍開著舊頁面的使用者，避免新舊版本同時持續寫入。

任何先前準備的候選包，都要重新核對其適用的前後端版本及已部署程式，才可套用。

## 執行與核對

以下是核對項目，實際時序依上一節確認的相容性與窗口安排；不適用的發布項目略過，不把清單順序當成固定後端優先。

1. 依紀錄更新程式並讀回比對；GAS 入口函式不得重複，不能為了「測一下」執行 `setup` 或初始化正式資料。
2. 更新已確認的部署，記錄實際版本及執行身分。GAS 的儲存、新版本建立、更新部署是不同步驟。
3. 只在已確認無副作用的前提下讀取正式版本／能力資訊。未知端點不得靠試送 POST 或空資料來探測。
4. 合併前核對人的明確決定、精確 PR head 與 base，以及必要檢查結果；缺少人的決定就保持 PR 開啟。新增提交後重新交付差異與受影響檢查，由人重新決定；base 有變更先核對整合影響，有新影響也須重新取得決定。同一 PR、同一 head 且範圍仍適用的有效決定不重問。仍有依賴的 PR 要保留提交關係，避免下游重複引入修改。
5. 確認前端發布工作對應預定提交；搭配已驗證的後端版本與假資料證據記錄結果。正式業務功能只觀察授權使用者的正常操作，不另創造正式資料作測試。
6. 記錄完成、部分完成或受阻，以及尚未驗證的範圍。若僅有 Pages 成功，不寫「整站驗收通過」。

## 回復

達到預先列明的失敗條件時，先停止本次發布，不繼續疊加其他 PR。由發布者依受限紀錄回復可相容的前端與 GAS 配對，回讀實際部署確認。

回復配對仍須符合已採用的隱私與授權要求，不得為了恢復可用性而自動重新開放公開入口、名單或匿名讀寫。沒有安全的回復配對時，改用受保護的維護頁或暫停相關功能，依已約定的窗口通知業務負責人。

程式回復和試算表資料復原是兩件事。直接覆蓋試算表可能抹掉備份之後同事的正常修改；未核對差異、可回復範圍及業務授權，不可拿備份整份蓋回。回復之後仍要檢查新欄位、未同步修改及舊分頁的處理方式。

## 發布後

更新受限位置的版本快照與待辦、實際部署配對、尚未解決的問題及回復紀錄；公開 README 只保留可公開的使用與維護說明。需要對同事公告時，先準備訊息，由已獲授權的窗口傳送；建立文件不等於已通知大家。
