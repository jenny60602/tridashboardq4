# AI 執行與一般同事驗收框架

目的：一般同事不必成為工程師，就能確認 AI 交付的結果。技術責任不因使用者缺乏 RD 背景而轉移給使用者。

## 三個判定互相獨立

| 判定 | 狀態 | 判斷方式 |
| --- | --- | --- |
| 技術準備度 `technical.status` | `UNKNOWN`／`BLOCKED`／`READY` | AI 蒐集並核對必要原始證據；失敗或不相容為 BLOCKED，缺證據為 UNKNOWN；必要項目完成才可 READY |
| 業務驗收 `business_acceptance.status` | `NOT_CHECKED`／`FAIL`／`PASS`／`NOT_APPLICABLE` | 同事確認假資料預覽是否符合需求；不得把未回覆當 PASS。純文件等無應用操作者可附理由標 NOT_APPLICABLE |
| 操作授權 `authorization.status` | `UNKNOWN`／`MISSING`／`GRANTED` | 對照使用者已授權的具體動作、對象與範圍；沿用有效授權，不重問。PR 合併必須另外有人的明確決定，綁定該 PR 與已交付 head |

「預覽符合需求」「技術證據足夠」「允許上線」是不同事。使用者願意承擔某項已說明限制，也不能把未執行的檢查改成通過。

`READY` 只涵蓋本次聲明的驗證範圍，不代表沒有任何缺陷。能否發布還要同時滿足必要業務驗收、具體發布授權、最新版本配對與回復要求。僅準備本機修改時不需要先取得發布授權；草稿預覽也不代表已准許部署。

## 唯一狀態來源

AI 從 [JSON 範本](../templates/change-record.template.json)建立每次變更紀錄。所有必要欄位都要填；缺資訊保留 `null`／`UNKNOWN` 並說明原因，不用空白假裝不適用。真實紀錄及證據放在核准的受限位置；若使用本機 `.private/changes/<工作編號>/`，須另確認存取控制。目錄名稱與 ignore 不能限制誰可讀檔，也不可提交正式資料或秘密。

同事驗收卡、PR 摘要與最終回報都依同一份紀錄產生；欄位衝突時先修正紀錄，不各自報喜。候選版本改變時，將受影響的檢查標為 `STALE`，重新執行後才更新狀態。

範本提供一致欄位，沒有內建檢查器、簽章或不可竄改保證；AI 仍需執行真實核對，後續平台門檻見本文末段。

## 執行步驟

### 1. 將需求轉成能驗收的行為

AI 從使用者描述整理「原本怎麼操作、修改後想看到什麼、誰會受影響」。只問無法從現有資料推定的業務問題，不要求一般同事選 branch、API、套件或 Git 衝突解法。

例如需求是「離線時不要丟修改」，可驗收行為是「使用虛構專案修改後中斷測試連線，再重新整理，能找回草稿且未擅自覆蓋伺服器」。AI 再負責推導儲存、授權、同步與逾時的技術檢查。

### 2. 查明基準與授權範圍

AI 唯讀核對 main、候選提交、正式發布來源、GAS 對應版本與已存在的授權。對已確認且未變的證據不重跑；來源有變才重新分析受影響部分。

記錄允許修改的範圍與禁止操作。正式網頁、試算表及備份不能作測試；公開位置不能新增機密文件。需要權限的工作先確認能力，不先改完才發現無法發布。

**任何專案檔案修改前，必須完成工作分支與 Issue。** AI 先從最新 `main` 或已確認的依賴基準實際建立並切換分支，記錄基準與名稱；再依 [Issue 範本](../.github/ISSUE_TEMPLATE/ai-change.md)建立追蹤，寫明問題、範圍與驗收條件。同一工作已有適當分支或開啟 Issue 時先核對再沿用。這也適用 Markdown 與緊急修正，唯讀調查可以先做。

AI 將分支、Issue 與後續 PR 對應記入同一份變更紀錄；公開內容只用可公開概述，內部證據留受限位置。建立分支或 Issue 受阻時，回報具體缺口、準備提案草稿，不跳過此步驟修改專案，也不謊稱已建立。

### 3. 在隔離位置完成修改與驗證

AI 製作修改、假資料預覽與符合風險的檢查。技術證據不能只寫「87 項通過」，必須記錄檢查目的、精確版本、環境、執行方式、結果、原始證據位置及限制。

| 改動類型 | 必須補足的技術證據 |
| --- | --- |
| 純文件 | 連結、內容一致性、格式及 diff 範圍；應用程式檔案內容未變。文件合併可能觸發靜態網站重新發布，須如實記錄 |
| 畫面或操作 | 對應情境的假資料互動、既有流程、實際畫面；不能只交截圖而不驗證操作 |
| 登入或權限 | 未授權請求遭拒、角色範圍、登出／到期與晚到回應；畫面隱藏不能證明資料沒回傳 |
| 儲存或同步 | 未同步草稿、失敗／逾時、重複請求、多人修改及資料不被誤覆蓋；全部使用假資料 |
| 前後端約定 | 動作、憑證方式、回傳欄位、資料格式與角色的相容矩陣；不能只比 API 數字 |
| 公開範圍或入口 | 倉庫權限與網站權限分開；主網域、原站、預覽與直接資源路徑的假資料檢查 |
| 正式發布 | 已驗證候選版本、權限、實際部署配對、無副作用的核對方式與安全回復計畫 |

每項檢查狀態限定 `NOT_RUN`／`PASS`／`FAIL`／`STALE`／`NOT_APPLICABLE`；不適用必須寫理由。測試紀錄不得含正式名單、登入碼、token 或財務資料。獨立審查應記錄檢查者與證據，不以第二個 AI 同意作為替代。

### 4. 提供一頁同事驗收卡

使用[驗收卡範本](../templates/acceptance-card.md)。每個業務情境用「做什麼 → 預期看到什麼 → 實際證據 → 同事的判斷」表達，預覽連線必須隔離。敏感資料可見性應使用虛構名稱與金額示範。

AI 不能替使用者填「已驗收」，也不能把 AI 的技術測試結果放進同事回覆欄。使用者有明確提供過驗收結果時可沿用，須綁定適用版本；修改影響已驗收行為時再請確認。

### 5. 根據狀態前進，不問籠統的「要不要繼續」

修改以連結 Issue 的 PR 交付。必要證據未齊時保持草稿；完成檢查不等於可自行合併。人看過交付結果後，可自行合併或明確指示 AI 代為合併特定 PR。AI 記錄該決定對應的 PR、head 與可信授權來源，不要求一般同事輸入技術版本。

沒有人的明確決定，AI 不得合併、啟用 auto-merge 或加入 merge queue。一般「繼續」、開 PR 的要求、業務驗收、READY、CI 綠勾及其他 PR 的合併授權，都不是本 PR 的合併決定。新增提交後須重新交付差異與受影響檢查，並由人重新決定；base 更新時核對整合影響，有新影響也須重新交付及取得決定。同一 PR、同一 head 且範圍仍適用的明確決定才可沿用。

| 情況 | AI 的下一步 |
| --- | --- |
| 缺口能靠現有權限與安全環境補足 | 繼續完成，告知實際進展 |
| 技術 UNKNOWN／BLOCKED | 說明哪個必要證據缺少或失敗、影響哪一步、需要的資料或權限；不請一般同事批准跳過 |
| 只是業務行為待確認 | 交付具體假資料情境，請同事回答符合／不符合與原因 |
| PR 檢查完成，但人尚未決定合併 | 交付 PR、Issue 與驗收卡，回報「待人決定合併」；保持開啟，不自行啟用自動合併 |
| 人已明確指示 AI 合併該 PR 的已交付版本 | 核對最新 base、head 與必要證據，符合條件後代執行；同一有效決定不重問 |
| 其他發布條件具備且該動作已授權 | 依發布手冊執行，不重複詢問同一授權；發布授權不能代替 PR 的人工合併決定 |
| 發布條件具備但動作未授權 | 說明具體目標、變更與影響後請求該動作授權 |
| 使用者回報「AI 說完成但畫面不對」 | 保留證據、重現於假資料環境，更新狀態；不要求使用者自行讀程式除錯 |

### 6. 分別記錄交付與上線

`delivery` 分別記錄本機修改、遠端提交與合併；`delivery.frontend` 與 `delivery.gas` 再各自記錄發布、部署後核對及實際版本。GAS 必須綁定專案 ID、部署 ID 與版本，不能只填可能重複的「版本 8」。這些識別資訊保存在私有紀錄，不貼到公開 PR。

建立 PR 後若尚未有人決定合併，`delivery.merged` 保持 false，`authorization.remaining_decisions` 明列待決定的 PR 與候選版本。建立 Issue、推送分支或開 PR 的授權，不能擴張為合併授權；實際決定記在 `authorized_operations_and_targets` 與 `trusted_request_references`。不要因工作已交付而提前關閉 Issue；追蹤是否結案以人的決定及實際結果為準。

各部署對象的 `applicability` 限定 `UNKNOWN`／`APPLICABLE`／`NOT_APPLICABLE`；不涉及該對象時附理由標 NOT_APPLICABLE。只有實際完成的欄位可為 true。前端發布成功不能推論 GAS 已更新，發布失敗也不能用「程式已提交」當成整項完成。

RD 使用者可以展開技術附錄參與深入審查。一般同事只看驗收卡；背景不同只改呈現方式，不改必須取得的技術證據。

## 不可混淆的三個判定

- 先前準備的候選程式不代表現在仍可部署；發布前必須核對目前前後端的實際約定。
- 舊分支測試通過，不代表新 main 或新增欄位也通過；證據必須綁定確切候選。
- Pages 發布成功，不代表 GAS 更新成功或公司名單已保密；每個主張要有自己的證據。

## 規則何時才算真正落地

本次框架只提供指令與範本，不自動安裝檢查器、設定必過 CI、main 保護或發布權限隔離。每次紀錄的 `enforcement.status` 預設為 PENDING；只有取得實際生效證據後才能更新。文件本身不能阻止不遵守規則的 AI。

後續應在受控的私有環境實作：

1. 工作環境預設只有必要權限，測試沒有正式資料憑證；可行時限制測試外連。
2. CI 在獨立環境重跑必要檢查，將證據綁定候選提交，拒絕缺少、過期或失敗的紀錄；不能只相信 AI 填入的 PASS。
3. main 與發布權限受保護，合併須有人明確決定，只有符合檢查與具體授權的流程能發布。
4. 驗收卡連到受控流程產生的證據。檢查器只能驗證其涵蓋事項；欄位齊全不等於程式正確，業務驗收仍須保留。

不因使用者是 RD 就默默解除這些限制，也不因一般同事說「可以」就把平台保護或未知結果當成已通過。
