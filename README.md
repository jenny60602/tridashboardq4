# tridashboardq4

專案儀表板與 AI 協作規範。本倉庫使用 `main` 作為預設分支。

## AI 執行，同事確認成果

一般同事只需說明想完成的工作、預期操作與不能接受的影響。AI 負責版本核對、影響分析、隔離測試與證據整理；同事透過具體情境驗收，不必閱讀程式或替未知的技術風險背書。

日常使用三個入口：

1. **AI 先讀 [AGENTS.md](AGENTS.md)**，依 [AI 工作流程](docs/AI_WORKFLOW.md)執行，再按改動範圍選讀其他文件。
2. **AI 建立一份[變更紀錄](templates/change-record.template.json)**，記錄版本、範圍、證據、未解問題及授權。實際紀錄與內部證據放在核准的受限位置，不要提交到 Git。若使用本機 `.private/changes/<工作編號>/`，仍須另確認存取控制；目錄名稱及 ignore 規則不提供保密保證。
3. **同事查看[單頁驗收卡](templates/acceptance-card.md)**，用隔離的假資料預覽確認操作與影響。驗收卡、PR 摘要及最終回報必須來自同一份紀錄。

技術準備度、業務驗收、操作授權分開判斷。缺證據保持未知，不能用使用者點頭、另一個 AI 同意或一個綠勾替代實際驗證。

## 修改與驗證

**固定流程：AI 建立並切換工作分支 → 建立 Issue → 修改與檢查 → 建立連結 Issue 的 PR → 人決定是否合併。** 文件修改也適用。從最新 `main` 或已確認的依賴基準開分支；同一工作已有分支與 Issue 時先核對再沿用。不要把下載的舊版檔案直接上傳覆蓋正式分支，也不要把未審閱的其他 PR 一起帶入。

PR 預設保持開啟。人可自行合併，或在看過交付結果後明確指示 AI 代為合併該 PR 的已交付版本；AI 不得自行合併或啟用自動合併。一般「繼續」、檢查通過與先前其他 PR 的授權都不算本 PR 的合併決定；新增提交須重新交付並由人決定。一般同事只需確認成果及是否合併，版本核對由 AI 負責，詳見 [AGENTS.md](AGENTS.md)。

測試一律使用完整虛構資料與隔離服務。啟動任何本機網頁或預覽前，先確認它不會連線正式資料來源；本機開啟檔案不代表已隔離。正式網頁、試算表與資料備份不得作測試。

純文件變更檢查內容、連結、JSON 格式及 diff 範圍，不需要操作正式服務。應用程式變更依 [AI 工作流程](docs/AI_WORKFLOW.md)選擇必要的假資料驗證。

## 規則與強制機制

這套文件提供 AI 的工作契約與驗收格式，不會自動建立 CI、分支保護、私有化或發布權限隔離。是否已啟用強制機制，必須由實際設定及執行證據確認，另記在受限的維運紀錄。

前端發布、GAS 更新與功能驗證要分別記錄；不能用「已合併」或「發布成功」概括未完成的其他步驟。詳細部署識別資料、內部版本盤點與問題證據不放在公開 README。
